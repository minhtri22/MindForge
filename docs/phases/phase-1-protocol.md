# Phase 1 — Compact End-to-End Kernel Protocol

Protocol version: **1.0 — frozen before implementation validation**
Base commit: `bba9360b87c947202115386a3c6ea1f68b9735b9`

## Objective and scope

Consolidate the validated Phase-0 path into one small reusable package:

```text
prepared UTF-8 text → tokenizer → token arrays → decoder Transformer
→ single-device training → checkpoint → independent evaluation → generation
```

Phase 1 is engineering consolidation. It contains no continual learning, replay, memory, adapters, plugin/callback systems, registries, distributed training, serving, quantization or speculative extension interfaces.

## Tokenizer and data inputs

The one supported tokenizer is byte-level BPE with NFC normalization, ByteLevel pre-tokenizer/decoder, and fixed special tokens in order: `<|endoftext|>`, `<|unk|>`. Default vocabulary is 16,384. Training accepts one or more UTF-8 files; load/save uses the tokenizers JSON artifact. Metadata includes its SHA-256 and structural identity.

The kernel accepts prepared UTF-8 train/validation files or pre-tokenized `.npy` arrays. It performs no web acquisition. Data preparation records source hashes, token-array hashes, tokenizer fingerprint and a combined dataset fingerprint. Batch starts are generated by NumPy `default_rng(seed + step * 1,000,003 + micro * 10,000,019)`; the same seed/data/config/step yields the same CPU batch. Cross-device floating-point bitwise identity is not promised.

## Device policy

`auto` deterministically selects XPU, then CUDA, then CPU. Explicit unavailable device requests fail without fallback. Supported dtype requests are `auto`, `float32` and `bfloat16`; CPU `auto` is FP32, XPU/CUDA `auto` is BF16. Small functions provide synchronization and allocated/peak memory where the backend exposes it. There is no backend class hierarchy or custom kernel.

## Checkpoint format

Torch checkpoint mapping, `format_version = 1`, containing:

```text
model_state
optimizer_state
step
model_config
training_config
tokenizer_fingerprint
dataset_fingerprint
seed
metadata
rng_state: Python, NumPy, Torch CPU, optional XPU/CUDA
```

Load rejects absent fields, unknown versions and model/config mismatch. Resume restores optimizer and RNG states. CPU resume equivalence is frozen at exact tensor equality and absolute loss delta `0.0` for the deterministic fixture. XPU resume is a functional gate: load, continue, finite loss and evaluable/generatable checkpoint.

## Evaluation contract

The independent evaluator loads only checkpoint, tokenizer and token array. It reports summed NLL, cross-entropy, bits/token and BPB. BPB is:

```text
summed natural-log NLL / (log(2) * represented UTF-8 bytes)
```

The byte count is obtained by decoding each target window with special tokens retained and measuring actual UTF-8 bytes. Frozen windows are evenly spaced and deterministic. Two evaluations must have CE and BPB absolute deltas at most `1e-6`.

## Generation contract

Prompt IDs are cropped to the model context for each autoregressive step. Greedy generation is the default (`temperature = 0`). Optional temperature and `top_k` use a CPU-seeded generator so fixed checkpoint, prompt, configuration and seed reproduce token IDs. Generation fails on empty prompts, invalid parameters or non-finite logits; no chat templates or server exist.

## QA and parity gates

The Phase-1 PASS gate is the 15-item gate in the authorizing prompt. CPU smoke uses a committed multilingual fixture and a tiny model. XPU validation must exercise BF16 forward/backward, optimizer, checkpoint, resume, independent evaluation and generation in a sustained but bounded run.

Phase-0 parity uses the exact frozen Baseline-0 checkpoint/model/tokenizer/data artifacts when locally available. The independent Phase-1 evaluator must reproduce Phase-0 final BPB within 10% relative. A reduced equivalent training comparison must keep Phase-0 and Phase-1 configuration/data/budget equal; Phase-1 throughput may not be more than 25% slower and peak memory may not be more than 25% higher. If exact artifacts are unavailable, parity is `REVISE`, not waived.

## Gate decisions

- **PASS:** every required kernel, CPU, XPU, checkpoint/resume, evaluator, generation, provenance, error-path, parity, test and documentation gate passes.
- **REVISE:** the core works but any major gate remains unresolved or parity exceeds a frozen tolerance.
- **STOP:** the compact-kernel approach is infeasible on the validated machine.

Implementation bugs may be fixed without changing this scope or the frozen gate thresholds. Any protocol change must be explicit and versioned before rerunning affected final evidence.
